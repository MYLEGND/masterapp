## Product contract

Founder manages the LEGEND® site, each agent manages their Protect site, and each business owner manages their own business site. All three use **one document contract, editor, element identity system, publish/version pipeline, management controls, signal catalog, analytics query service, destination resolver, dispatch policy, consent rules, and CRM domain services**. Content, data, credentials, page history, and permissions remain isolated by the permanent owner. The same controls render inside the relevant authorized profile and workspace; application shells can differ without copying business logic, pages, CSS rules, or state.

An editor may choose what a button, form, section, video, booking component, or checkout means for *analytics*. Only a verified server outcome can claim `Lead`, `AppointmentBooked`, `Purchase`, `PolicyPaid`, or another server-authority conversion. Profile is the connection authority. Website Analytics is the operational view. CRM reads the same persisted person/lead/client records and outcomes produced by the canonical capture path.

## Database contract and migrations

1. **Owner key:** use a typed `MarketingOwnerScope` value (Founder, Agent, Business; site key; `AgentTrackingProfileId` or `CommerceBusinessId`) constructed only after existing authorization and verified routing. Its storage representation has explicit typed nullable FKs and a check constraint allowing the applicable owner combination. Founder has a unique global site key. Protect must have an agent ID. Business and Parfait must have a commerce business ID. Keep the current `WebsiteContentState` as the website owner record; no second website owner table.
2. **One connection table:** a `MarketingConnection` with owner fields, provider, Meta ad account, Meta Business Manager ID, dataset/Pixel ID, encrypted credential, expiration, status, verification timestamps, rotation audit, and row version. Filtered unique indexes enforce one active connection per owner/provider/dataset policy. Encrypt secrets with the already shared Data Protection authority or a reviewed central secret reference; reads return redacted status. Migrate each existing encrypted token using its original app/protector while it can still decrypt it, verify the central read, and avoid copying plaintext into migration logs. The business ID field must be named `CommerceBusinessId`, distinct from `MetaBusinessManagerId`.
3. **Published mappings:** add typed `WebsiteSignalBinding` entries inside the *existing* `WebsiteContentDocument`; sanitation enforces element ID, trigger, catalog name, delivery mode, allowed source fields, consent category, and bounds. A `WebsiteContentVersion` snapshot makes mappings immutable with content. A separate index/projection table, if needed for efficient Event Map queries, is derived transactionally from that exact version and has no independent editing authority.
4. **Owner columns on events:** add nullable typed `CommerceBusinessId`, `SiteKey`, `WebsiteContentVersionId`, `BindingId`, and consent/dispatch decision fields where missing in `AnalyticsEvent` and `MetaSignalEvent`. Retain existing agent columns; new writes must supply exactly the applicable owner set. Add composite owner/time and owner/event-id indexes and durable uniqueness appropriate to producer and destination. Backfill only from authenticated provenance (verified host, published version, lead/order link, known agent). Ambiguous legacy records remain quarantined from business reads; never infer ownership from a JSON substring or a visitor/session ID alone.
5. **CRM provenance:** add business ownership to the existing canonical lead/client relationships where needed, with source inquiry/submission/version IDs. A business contact may also be an agent client; authorize each relationship separately. `WebsiteLeadSubmission.ResolveId` currently includes agent ID, page and email but no commerce business ID: introduce a versioned business submission identity without changing IDs of existing agent retries. Reconcile the current launch-audit handoff before modifying this key. Avoid duplicating PII into a new marketing contact store. Consent evidence is versioned and associated with the original capture/outcome, not inferred from the presence of an email.
6. **Transition:** additive migration and indexes → backfill plus reconciliation report → shadow-read comparison using sanitized counts only → switch canonical reads/writes to SQL authority → disable superseded cache/file write paths → remove old paths after the agreed observation window. Do not run a permanent dual-write, silent fallback, or competing credential resolver. Keep reversible release flags for the new UI and event dispatch without reverting the schema or erasing customer data.

A newly added button starts at **Off**. A user can select `click → LeadFormStart` for eligible browser analytics/Pixel, or `successful saved submission → Lead` only when the server producer supports the outcome. A booking link click is intent; a confirmed booking is `AppointmentBooked`. A checkout button click is intent; a verified paid order is `Purchase`. The inspector explains any unavailable event and links to the required form/booking/checkout integration. Website-wide defaults are templates for new elements, not silent overrides of explicit bindings.

**Data fields:** email, phone and name can only be selected from approved, validated form/CRM fields with appropriate marketing consent; sensitive/protected fields are excluded. A field-focus event never sends the field value. The browser sends an opaque event ID, site version, binding ID, trigger and first-party context. The server resolves the destination and allowed matching fields, normalizes/hashes when eligible, and excludes missing/unconsented values. No URL, element ID, browser mapping, logs, or test trace contains raw contact data or CAPI tokens. Analytics consent and advertising consent have separate decision states; suppressed Meta events remain visible as sanitized diagnostics when permitted. Existing `MetaConversionsApiService` performs outbound normalization/hashing.

## Event transaction and acknowledgement

1. Verify host or authenticated operation, resolve permanent owner and current published version. An editor session has explicit preview/test mode and cannot create a production lead or production marketing event.
2. Match the element/trigger against the immutable published binding and central catalog. Reject foreign version, forged owner, unknown element, disabled mapping, unexpected form source, unsupported trigger, or expired permission.
3. Persist first-party analytics with the typed owner and event ID. For verified conversion, commit the canonical lead/booking/order outcome and its Meta-signal outbox record in the same database transaction. Repeated form submission reuses the existing scoped record. Browser input never certifies a purchase or booking.
4. Evaluate marketing consent and destination health, then let `MetaSendAuthority` decide send/suppress/dedupe. The one dispatcher claims rows durably by owner/destination/event. Retry transient failures and record sanitized response, acknowledgement, attempt count and terminal state.
5. When both Pixel and CAPI send the **same authorized event**, use the same event name and ID across the pair. Do not pair a click-intent event with a later verified conversion merely to force deduplication. Meta documents same `event_name` and `event_id` for deduplication of matching browser/server events (official [Conversions API implementation guidance](https://developers.facebook.com/documentation/ads-commerce/conversions-api/guides/end-to-end-implementation)).
6. Analytics UI distinguishes observed action, accepted ingestion, suppressed decision, queued attempt, Meta accepted response and failure/retry. A call to Pixel is never presented as confirmed delivery to Meta.
